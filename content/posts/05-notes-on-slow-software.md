前些年我曾经清理过自己维护的一个旧网站项目。仅仅隔了两年半没有动过源码，重新拉下代码想改几行文字时，构建工具却因为某个底层依赖的次版本号废弃而彻底罢工。为了修改一个逗号，我不得不花掉一整个周六的下午升级锁文件、排查插件兼容警告、甚至重构配置语法。

那次经历让我开始认真思考一个问题：**为什么在硬件算力呈指数级增长的今天，维护几篇静态文章的成本反而变得越来越脆弱？**

## 什么是“慢软件”

“慢软件（Slow Software）”并不是指运行迟钝的软件，恰恰相反，它指的是像慢食运动或老式机械表一样，**在设计时就刻意抵制无意义的依赖膨胀与频繁重写的软件**。这类工具往往具有以下几个共同特征：

- **可被一个人完整理解**：全部源码加起来不过几百上千行，没有藏在几十层目录底下的魔法约定，任何时候打开都能在二十分钟内看清全貌。
- **纯文本作为第一等公民**：内容以 `.md` 和 `.json` 存储，即便某天构建脚本真的失效，人类依然可以直接用任何文本编辑器读懂每一篇文章与元数据。
- **零隐性网络耦合**：构建过程不向远端下载字体、图标包或统计脚本，输出产物可以原封不动地放进 U 盘或任意静态目录长期归档。

> 真正昂贵的从来不是第一次写出代码的时间，而是未来五年里每次回来看它时，你必须付出的心智重启成本。

## 一次典型的极简构建与验收节奏

在本站的设计中，我们将日常内容维护浓缩成三条直截了当的终端命令：先生成静态产物，再运行后端单元测试与全站门禁校验，最后用本地预览服务器检查实机渲染效果：

```bash
# 1. 清理并全量构建静态站点产物至 dist/
python scripts/build.py

# 2. 执行后端单元测试与全站死链/契约门禁检查
pytest tests/test_backend.py -v
python scripts/check.py

# 3. 启动本地静态预览服务器进行人工抽查（Ctrl+C 退出）
python scripts/serve.py --host 127.0.0.1 --port 8080
```

### 什么时候该拒绝引入新工具

在动手做任何个人基础设施之前，不妨先问自己三个简单的问题：

1. **这个问题真的需要一个外部依赖吗？** 许多需求——比如 Frontmatter 解析、轻量模板替换、甚至站内模糊搜索索引——在边界清晰的情况下只需几十行标准库代码就能解决得干净利落。
2. **如果这个库明年停止维护，我需要多久才能替换它？** 对于 `Pygments` 这样接口稳定二十年的工具，我们可以放心依赖；而对于生命周期短暂的构建插件，则要慎之又慎。
3. **五年后我换了一台全新电脑，重现这套环境需要几步？** 依赖越少，未来的自己就越自由。

## 把精力留给真正重要的事情

写代码本身固然充满乐趣，但个人网站归根结底是一座承载观点、记忆与作品的居所。当我们用减法工程把构建层打磨到稳如磐石之后，工具就完成了它最崇高的使命——**退居幕后，不再打扰写作本身**。

或许十年之后，前端生态又已经经历了好几轮框架更迭，但我依然希望届时打开这个仓库时，只需敲下一行熟悉的构建命令，这本小小的数字出版物便能像今天一样安静而完整地亮起。
